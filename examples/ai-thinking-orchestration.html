01 · Three regimes

不是升级关系，是三档预算

同一模型
三种花法

差别不在参数规模，而在生成多少 token、验证多少次、允不允许回溯。

Regime A

直接回答

一次前向，输出即答案。延迟最低、成本最低。

擅长　改写、翻译、分类、抽取

失效　多步计算、需要核对事实

典型预算　1×

Regime B

思维链

显式写出中间步骤，再给结论。可读、可被人工检查。

擅长　多步推理、过程需要审计

失效　步骤连贯但结论仍错的"假踏实"

典型预算　4–8×

Regime C

推理搜索

采样多条路径，用验证器挑一条。准确率上限最高。

擅长　有标准答案、可自动判分的难题

失效　没有可靠验证器时等于抽样赌博

典型预算　16–64×

关键判断：先问"这个任务能不能被自动验证"。 能验证 → 加宽加严都划算；不能验证 → 加算力只是把同一个错误说得更自信。

判定按钮 1

有单测 / Schema / 标准答案？　→ 走 C

判定按钮 2

只能人工判断，但错一次很贵？　→ B + 人工复核

判定按钮 3

错了改一下即可，且高频？　→ A，不要思考预算

02 · Budget curve

算力加在哪里，决定曲线怎么弯

示意图
量级参考公开研究

读图三件事

① 灰色虚线是"直接回答"：加预算它一动不动—— 没有搜索的模型不会因为等得久而变准。

② 思维链在 8× 之后趋平：单条链的长度收益有天花板。

③ 推理搜索在 16× 之后仍在涨：因为验证器把多出来的候选转成了正确率。

拐点：8×–16× 之间。低于它，加宽没意义；高于它，必须先有验证器。

读法提示：横轴是对数刻度，视觉上的"最后一小段" 其实是 32×→64×，成本翻倍。

反直觉点：在 4×–8× 区间，思维链一度领先于搜索—— 因为搜索的候选还没多到能让验证器挑出差别。别只看终点，要看交叉点。

03 · Anatomy

思考的四个动作，缺一个就退化成猜

循环
不是流水线
1

拆解

把问题切成可独立验证的小步，并标出最易错的一步。

→
2

生成

只针对最易错的一步生成多个候选，而不是整题重来。

→
3

验证

规则、单测、检索比对，或第二个模型的独立意见。

→
4

回溯

失败就退回上一步，而不是在错误前提上继续推。

同一个任务，四个动作分别落在哪（以"合同条款冲突检查"为例）

动作这一页要做什么具体做法
拆解把"是否冲突"拆成逐条比对抽出条款 → 对齐主题 → 逐对判断，标出最易错的"主体范围"
生成只对存疑条款生成多个判断对 3 条可疑条款各采样 5 次，其余条款单次判断
验证用规则与引用交叉核对条款编号必须存在、引用的法条必须可查、金额必须回算
回溯失败就退回抽取重来抽取缺页 → 回到 PDF 分页重取，不要在缺页上继续判

真正的增益来自"验证"

验证器可以是单元测试、JSON Schema、检索比对、 计算器、第二个模型的独立意见。没有验证的思考，只是更长的草稿。

回溯比长度更重要

多数失败不是"想得不够久"，而是"错了也不回头"。 给模型一个显式的失败信号，比再给它 2000 个 token 有效得多。

04 · Verifier

有验证器与没验证器，是两条曲线

示意图
同一模型同一题集

同一条曲线，两种命运

两条线在 n = 1 时几乎重合——起点一样。 分开它们的不是采样数，是验证器。

为什么投票会退化

没有独立判据时，多数票只是"多数派的口音"： 错误答案若同样高频，投票会把它选出来。样本越多，反而越自信地错。

可落地的验证器：单测、Schema 校验、检索比对、数值复算； 没有其一，就不要声称"多采样提升准确率"。

成本提醒：n = 32 意味着 32 次采样。若验证器只能过滤 1/3， 实际有效样本只有 10 条左右——先测验证器的判别力，再决定 n。

04 · Verifier
07 / 16
这页最容易讲错：不是"多采样一定更好"，而是"多采样 + 可靠判据"才更好。 没有判据时，自一致反而会放大系统性偏差。

什么时候值得让 AI 多想一会儿

一张卡
按顺序问四句
四个提问

Q1　答错了代价多大？（钱、合规、信任）

Q2　我能自动判断对错吗？（有测试/规则/检索）

Q3　这个任务一个月跑几次？（决定蒸馏价值）

Q4　延迟预算有几秒？（决定能不能并行）

结论：Q1 高 + Q2 能 → 上搜索与验证；
Q1 高 + Q2 不能 → 上多专家 + 人工复核；
Q1 低 → 直接回答，不要思考预算。

四条经验规则
1

可验证 → 加大投入

有测试、有标准答案、有检索依据。

2

不可验证 → 降低承诺

改成"给选项 + 说明不确定"，而不是硬答。

3

高重复 → 先蒸馏

把想清楚的过程固化成规则或小模型。

4

低风险 → 直接回答

改写、路由、格式转换不需要思考预算。

06 · Sparse experts

参数量涨十倍，计算量只涨一点

门控 + top-k
示意权重

门控网络 g(x) 给每个 token 打分，只把分数最高的 k 个专家算完再加权求和。 模型因此可以很"大"，但每次只算很小一部分。

它解决的是容量，不是推理。专家是"不同语料上训练出的子网络"， 不是"可以按业务点名的顾问"。

代价：显存要装下全部专家；路由不均会让专家闲置； 训练时容易出现"赢者通吃"。

与 Part 02 的区别：这里的选择由训练出的门控完成， 业务说不清"为什么是它"。要可解释、可替换，得用系统层编排（P11）。

容量视角

总参数 = 全部专家之和；单次计算 ≈ 前 k 个专家。

成本视角

显存按全部专家算，算力按 top-k 算。

业务视角

不可点名、不可解释——需要可解释就用外部编排。

07 · Orchestration

并行不加延迟，串行吃满预算

同一条链
总延迟 3.6s

路由器先判意图，专家并行执行，最后串行汇总与校验。 加专家只增加成本；延迟卡在串行段。

三个可操作结论

① 加专家 = 加成本，不加延迟。要更快就别加专家。

② 汇总占 19%：拆成"校验"与"合并"两条并行支路，能立刻省下 0.3s。

③ 路由只占 11%，却决定后面 89%：路由错一次，后面的算力全白费。

经验阈值：交互式场景把串行部分压到总延迟的 35% 以内； 否则用户会感知到"点了没反应"。

08 · Policies

四种调度策略，落在同一张代价图上

横轴延迟
纵轴单次成本

选型口诀

先规则，再模型路由，最后才考虑学习式门控。 绝大多数业务在第 2 个点就够。

混合是常态

规则兜底 + 模型路由主判 + 投票只用于高风险分支， 是成本与可靠性最平衡的组合。

别忽略纵轴

成本是每次请求的倍数。日活一万的系统， 从 2× 挪到 26× 就是每月多出的六位数账单。

怎么验证"能往下走"

用 1% 流量做影子对比：新策略与现策略同时跑，比对结论一致率与 P95 延迟，达标再放量。

09 · Failure modes

错误沿链路累积，比想象得快

单步 95%
六步之后？

读图

每步 95% 听起来很稳，但六步串联后只剩 74%。 链路每加一个节点，就是在给正确率做一次乘法。

错误传播

上游错一步，下游在错误前提上继续推，最终错得很自信。

过度调用

简单问题也开五个专家，延迟与账单一起失控。

修复三条：① 每个节点自带校验，失败即中断而非继续； ② 关键节点要求引用与依据；③ 给简单请求一条短路，不进专家链路。

算一笔账：把每步做到 99%，六步后仍有 94%； 把链路从 6 步压到 4 步，95% 也能到 81%。减节点比提精度更便宜。

路由要可解释

能说出"为什么叫它"，出错时才分得清是路由错还是专家错。

专家要窄而深

一个专家只做一件事。宽泛的"万能专家"等于没有专家。

汇总是真瓶颈

多个专家给出冲突结论时谁说了算？这条规则必须提前写死。

迁移路径：从规则到模型路由，最省事的四步

阶段做的事验收标准

11 · One thing

想得久，是内部调度变密集；
叫得多，是外部思考变分散

内部 · 单个模型

思考 ≈ 调度。注意力头、专家层、控制 token 的分配， 本质上都在决定"这一步让谁多算一点"。

加深的方式：更多中间步骤、更多候选、更多验证。

外部 · 多个智能体

调度 ≈ 思考。路由、专家、汇总、回溯这四件事， 就是一个系统在外部模拟"想清楚再说"。

加宽的方式：更多专家、更清晰的路由、更强的仲裁。

两者的分界线不是技术，是预算—— 你愿意为一个正确率多付多少延迟与成本。

同一件事的两种做法（对照）

内部加深　思维链 + 自一致 + 验证器； 改的是单次请求，延迟几乎不变、成本上升。

外部加宽　路由 + 多专家 + 汇总； 改的是请求的走向，延迟上升、单专家成本不变。

共同前提　两者都要有"判对错"的能力， 否则只是在放大同一种偏差。
